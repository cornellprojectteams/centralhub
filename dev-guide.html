Developer guide

Working on the hub

How to edit and publish this site from a browser with GitHub Codespaces and Copilot, and how the Apps Script projects behind it work and go live. For running things day to day, use the admin guide.

Requirements Open a Codespace Files Preview Use Copilot Publish Recovery Apps Script projects Space Status engine Routes and setup Command Center API Links

01Requirements

  • A GitHub account with access to cornellprojectteams/centralhub. If the repo shows a 404, ask to be added as a collaborator.
  • For the scripts: edit access to the Apps Script project or the Google Sheet it is bound to.

02Open a Codespace

  1. Open the repository.
  2. Click the green Code button, select the Codespaces tab, click Create codespace on main.
  3. Wait about a minute. VS Code opens in the browser with the site's files loaded.

To continue later, reopen the same codespace from that menu instead of creating a new one.

03Files

  • index.html The staff page.
  • admin.html The admin page: day-to-day tools. Not linked from the staff page.
  • developer.html The developer page: script projects, the repo and this guide.
  • command-center.html The ops dashboard. team.html One team's open issues, for sharing.
  • inventory.html, inventory.js, inventory.css The inventory app.
  • styles.css Colors, fonts and spacing for every page except the inventory app.
  • app.js Search, the slide-over panels and the section list, shared by the staff, admin and developer pages.
  • config.js The web app URLs and the inventory settings. Change a URL here, not in the pages.
  • docs.html The admin guide. dev-guide.html This guide. space-status-how-to.html The staff how-to.
  • apps-script/ Copies of the Apps Script code. The live code runs on Google; see Apps Script projects.
  • README.md More detail, including setting up the inventory.

04Preview

  1. Open a terminal: Ctrl + ` (backtick, under Esc).
  2. Run:
python3 -m http.server 8000
  1. Click Open in Browser in the popup.
  2. Edit, save (Cmd/Ctrl + S), refresh the preview tab.

The preview is private to your codespace. Nothing is public until you push.

05Use Copilot

  1. Open Copilot chat: the chat icon in the sidebar, or Cmd/Ctrl + Shift + I.
  2. Describe the change. Name the file and point at an existing element to copy its format. Examples:
  • "In admin.html, add a link to the fire safety training doc in the Compliance section, formatted like the other links there."
  • "In styles.css, make the footer headings slightly larger."
  • "In admin.html, add a section called Events with one link, following the pattern of the Fleet section, and add it to the section list."
  1. Review the proposed diff, then Accept. To edit one spot, select the code and press Cmd/Ctrl + I.

Make one change at a time and check the preview after each. If a suggestion is wrong, reject it and rephrase.

06Publish

In the terminal:

git add -A
git commit -m "add fire safety link to compliance"
git push
  • git add -A stages all changed files.
  • git commit -m "..." saves a checkpoint. The message should say what changed.
  • git push uploads it to GitHub.

Equivalent buttons: the Source Control icon in the sidebar. Type the message, click Commit, then Sync Changes.

GitHub Pages publishes the main branch to the live site within a minute or two. Hard-refresh (Cmd/Ctrl + Shift + R) if the change does not appear.

07Recovery

  • git status Lists what changed since the last commit.
  • git checkout -- filename Discards uncommitted edits to that file.
  • Pushed something broken? Every commit stays in history and any version can be restored. Ask for help before forcing anything.
  • Codespaces stop when idle; work is kept. Delete unused ones at github.com/codespaces.

Putting a change live

  1. Open the project, paste the changed file over the old one and save.
  2. The three web apps (Space Status, Command Center API, Inventory) only change after a new version: Deploy > Manage deployments > pencil > Version: New version > Deploy. The URL stays the same.
  3. Make sure the copy in apps-script/ matches what now runs, and publish it.

The site finds the web apps through config.js (Space Status and the inventory) and STATS_ENDPOINT in app.js and command-center.html (Command Center API). Those URLs only change if someone makes a new deployment instead of a new version. Setting up the inventory, and updating an older inventory sheet, are covered in the README.

09Space Status engine

One standalone project runs Space Status: the emails, the reminders and every web page (issue dashboards, team pages, the confirm page, projects and proposals). The Space Status Tracking sheet is its database.

On submit

The form-submit trigger is named sendEmails and calls onFormSubmit, which:

  1. Reads the row by header name. Column order does not matter.
  2. Looks the team up in Team Contacts. To: general email and liaison. Cc: safety lead, Extra CC and CONFIG.alwaysCc.
  3. Sends the email: subject by severity, deadline in bold, one action button.
  4. Stamps Issue token and Notified at on the row and shares any photo by link so the pages can show it.

If the team has no usable email, mail goes to CONFIG.fallbackEmail.

The trigger belongs to another account and cannot be deleted from this one. The script keeps a shim so it runs the current code:

function sendEmails(e) { onFormSubmit(e); }

Do not add a second on-submit trigger; teams would get every email twice.

Deadlines and reminders

The form question is Respond within; older rows and the sheet column may still say Current Status. parseColor_ maps both the old color labels and the timeframe answers to the same five levels. Windows are in SLA_DAYS and the email wording in SEVERITY, both at the top of 02_notify_on_submit.gs:

const SLA_DAYS = { red: 0, orange: 3, yellow: 10, ivory: 21, purple: null };

const SEVERITY = {
  red: { subject: 'Urgent: same-day action needed', ... },
  ...
};

sendReminders runs on a daily time trigger. Day 0 is covered by the first email. The first reminder goes on the due date, then they repeat at:

interval = max(1, round(windowDays / 2))  // days

The schedule counts from the Last reminder stamp, so a missed run catches up the next day. Rows that are approved (Addressed at), waiting for approval (Completed at) or purple are skipped.

Settings

Go-live settings, in CONFIG at the top of the script:

sender: 'eng_projectteams@cornell.edu',  // send-as alias on the running account
alwaysCc: ['nhh5@cornell.edu'],
fallbackEmail: 'nhh5@cornell.edu',
webAppUrl: '.../exec',  // must be the deployed URL; the email buttons use it

The columns the script writes (Notified at, Issue token, Addressed at, Last reminder, Completion photo, Completion note, Completed at, Sent back reason) are named in CONFIG and added when first needed. Completion photos and project uploads go to a Drive folder named Ops Hub completion and project uploads.

Pages opened with admin=1 show the admin controls with no passcode. Only the links on the admin page add it.

10Routes and setup

Every page is a route on the one web app URL (SPACE_STATUS_URL in config.js):

/exec                     team picker
?view=all                every team's issues (admin=1 adds the admin controls)
?view=Baja               one team's issues, read only (act=1 allows completing)
?team=TOKEN              a team's private page: complete jobs with a photo
?id=TOKEN                confirm page behind the email button
?module=projects         projects list (admin=1 adds the admin controls)
?module=projects-dash    projects dashboard
?module=proposals        proposal board (admin=1, back= link to the hub)
?registry=...            old registry links and labels: "Inventory has moved"

embed=1 on any of them drops the page header, for the hub's slide-over panels. The confirm page exists because mail scanners open links on their own; a plain link would close issues by itself. Nothing changes until a person clicks.

Setup and utilities

Run from the script editor. The setup functions are safe to run again.

  • setupTasksProjects Creates the Projects tab and the completion columns.
  • setupProposals Creates the Proposals and Proposal votes tabs. The rating thresholds are in the PR object at the top of 07_proposals.gs.
  • fillTeamTokens Gives every team on Team Contacts a private page token. Run it after adding a team.
  • sendReminders Sends due reminders now.
  • sharePhotos One-time backfill that makes older report photos viewable on the pages.
  • listResponseHeaders Prints the Form Responses headers to the log.
  • setupInventory (inventory sheet) Builds or repairs the inventory sheet and runs a self-test.

11Command Center API

A separate, read-only project. It reads the source sheets listed in SOURCES and returns one JSON payload, which the Command Center page and the badge on the Command button load JSONP-style. It shares no code or deployment with Space Status.

  • Results are cached for CACHE_SECONDS (3 minutes). After changing its logic, deploy a new version and bump CACHE_VERSION, or run clearStatsCache; otherwise the old output keeps showing until the cache runs out.
  • describeSources, peekFleetLog and peekFleetApproval print what the API sees in its sheets, for checking column names.
  • Its inventory numbers (mill room orders, locks) come from the old Tool inventory, purchasing and locks sheet, not the inventory app.
